
# Declarative UI의 의미를 설명할 수 있다.
Declarative UI(선언형UI)는 개발자는 결과값(data)의 변화만 정의하고, DOM 조작은 react가 대신해주는 시스템.

리액트 같은 경우, SPA으로 하나의 화면에도 수 많은 재활용 컴포넌트들이 있고 각각 흩어져있다.
마치 php의 include처럼 이럴경우 페이지를 빌드 해보지 않는 이상 그 수많은 DOM들을 체크 할수가 없다
기존 제이쿼리같은 Imperative UI(명령형UI) 도구들은 DOM을 직접움직여야 되기때문에 실무에서 사용했을때 
수많은 include페이지 때문에 해당 DOM을 찾기 조차 어려웠고 코드만 봣을때 실제 의도를 파악하기가 힘들었다.
하지만 리액트같은 Declarative UI(선언형UI) 도구는 useState 같은 행위로 변화시키고싶은 결과값의 변화를 통해 
react가 자동으로 DOM을 조작하기 때문에, 개발자 입장에서 조금 더 직관적으로 의도를 분석할수 있다.

# Component 실행과 DOM 업데이트를 구분할 수 있다.
Component 실행은 아직 구조화 되지않은 상태 즉, 메모리에 적재 되지않은 상태이다.
DOM 업데이트는 트리형태로 구조화된 상태. 이 이후 useEffect의 동작 시점이다.

# Render Trigger → Render Phase → Commit Phase 흐름을 설명할 수 있다. 
화면전체가 그려진 후 재랜더링을 하기 까지의 흐름.
- RenderTrigger : 사용자의 event발생 지점. 데이터 변화의 트리거지점.
- Render Phase : 메모리 연산 및 vitualDOM생성 지점. diffing알고리즘 실행되어 DOM업데이트 유무 판단.
- Commit Phase : DOM 업데이트 진행하는 단계.

(예시)
 function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>현재 숫자: {count}</p>
      <button onClick={() => setCount(count + 1)}>+</button>
    </div>
  );
}

1. 화면의 + 버튼 클릭시 setCount()가 1이 되는 직후 (RenderTrigger)
2. 연산 및 화면을 재구성해야 되는지 판단 (Render Phase)
3. 화면 갱신 (Commit Phase)

# Reconciliation이 무엇을 비교하고 왜 필요한지 설명할 수 있다. 
DOM 업데이트 전 DOM 조작 성능을 최소화하여 성능을 최적화 하기위해 virtualDOM의 비교를 선행하는 것. Current Fiber Tree(기존 virtualDOM)과 WorkInProgress Fiber Tree(준비된 virtualDOM)을 비교하여 노드단위로 필요한 곳만 갱신시킨다.

# Component Identity와 Render Tree의 관계를 이해한다. 
리액트는 트리(노드)구조로 설계되어 있고, 비교시 Render Tree상의 위치, 컴포넌트 타입, key 값을 근거로 Identity를 판단하여 DOM을 업데이트 시킨다. 이때 key값 부여시 같은노드에 위치한 3개의 요소가 있다고 할때, index로만 판단하지 않고 key값을 검사하여 엄밀한 비교가 가능하다.

속성이나 내용만 바뀌었을 때 (Identity 유지): 기존 DOM 노드를 그대로 두고 안의 값만 부분 변경함.

타입이나 key가 달라졌을 때 (Identity 파괴): 단순 업데이트가 아니라 기존 DOM 노드와 내부 state를 아예 삭제(Unmount)하고 완전히 새 노드로 교체(Re-mount)함.

# Re-render와 실제 DOM mutation이 같은 개념이 아님을 설명할 수 있다.

Re-render는 virtualDOM을 뽑아내는 과정이고, DOM mutation은 실제 브라우저 화면을 띄우기 위해 virtualDOM을 비교하여 새로운 DOM를 조작하는 과정이다.

따라서, DOM mutation은 리액트가 알아서 진행하기 때문에 개발자는 성능최적화를 위해 Re-render 과정을 최소화 시켜야한다.
