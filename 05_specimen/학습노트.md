# 1. UI / Client / URL / Server State를 구분한다.

상태의 성격과 저장 위치에 따라 명확히 4가지 영역으로 분리한다.

1) UI State
- 위치/생명주기 : 컴포넌트 내부 메모리 (`useState`) / 창을 닫거나 컴포넌트가 언마운트되면 소멸
- 관리 데이터 : 모달 열림/닫힘, 아코디언 토글, 탭 인덱스, 드롭다운 활성화 여부
- 특징 : 새로고침이나 페이지 이탈 시 날아가도 무방한 가장 가벼운 휘발성 상태

2) Client State
- 위치/생명주기: 브라우저 전역 메모리 (Zustand, Redux, Context API 등) / 새로고침 시 초기화
- 관리 데이터: 다크 모드 설정, 장바구니 임시 목록, 다단계 폼 입력 데이터
- 특징: 클라이언트 앱 전역에서 여러 컴포넌트가 공유하지만, 백엔드 DB와 즉각 동기화될 필요는 없는 프론트엔드 고유 데이터

3) URL State
- 위치/생명주기: 브라우저 주소창 (location.search, pathname) / 새로고침 및 뒤로 가기에도 영구 유지
- 관리 데이터: 검색 키워드(?keyword=react), 페이징 번호(?page=2), 필터링 조건, 상세 페이지 ID(/post/10)
- 특징: 새로고침해도 유지되고, 링크 복사로 타인과 공유 가능한 상태

4) Server State
- 위치/생명주기: 원격 DB / 백엔드 세션
- 관리 데이터: 게시글 목록, 유저 프로필, 주문 내역, 재고량
- 특징: 프론트엔드는 이 데이터의 소유권이 없다. 단지 네트워크 통신을 통해 특정 시점의 상태를 잠시 빌려와 화면에 비춰보는 '과거 스냅샷'에 불과하다.

---

# 2. Server State가 stale할 수 있다는 의미를 이해한다.

1) 프론트엔드가 API 통신을 통해 데이터를 받아온 바로 그 순간부터, 해당 데이터는 이미 과거의 기록이다.
2) 클라이언트가 화면을 바라보고 있는 수초 사이에도 다른 관리자가 DB를 수정했거나, 백엔드 스케줄러/배치 프로그램이 데이터를 변경했을 가능성이 항상 존재한다.
3) 즉, stale은 통신 오류나 버그가 아니라, "언제든 실제 원격 DB와 어긋날 가능성이 있으므로 정책에 따라 다시 가져올 준비가 된 만료 상태를 뜻한다.

# 3. Query Key가 cache identity인 이유를 설명한다.

Query Key는 TanStack Query의 전역 메모리(QueryCache)에서 특정 데이터를 식별하는 고유 기본키(Primary Key) 역할을 한다.

```tsx
// Query Key는 배열 형태로 직렬화(serialization)되어 고유 식별자가 됨
useQuery({
  queryKey: ['posts', { category: 'backend', page: 1 }],
  queryFn: fetchPosts,
});
```

- 동일 Key = 데이터 공유 및 네트워크 중복 호출 제거 (Deduplication) : 
  한 화면에 서로 다른 컴포넌트 5개가 같은 키(`['posts']`)를 바라보고 있어도, 실제 API 호출은 단 1회만 발생하고 캐시 데이터를 공유한다.
- Key 변경 = 새로운 캐시 엔티티로 식별 :
  page: 1에서 page: 2로 바뀌면 식별자가 달라졌으므로, 1페이지 캐시를 덮어쓰지 않고 새로운 캐시 슬롯을 생성하여 독립적으로 관리한다.

# 4. staleTime / refetch / retry의 역할을 구분한다.

데이터의 신선도 판정 -> 갱신 시점 -> 장애 복구 파이프라인으로 역할을 구분한다.

| 속성 | 핵심 질문 | 기본값 및 동작 원리 |
1) staleTime (신선도 유지 기간) 
속성 : "가져온 데이터를 몇 초 동안 최신(fresh)으로 인정할 것인가?" 
동작 : 기본값 0초. 가져오자마자 즉시 stale로 분류됨. 남아있는 동안에는 컴포넌트가 재마운트되어도 API 호출 없이 캐시를 즉시 반환함.

2) refetch (백그라운드 최신화 트리거) 
속성 : "데이터가 이미 stale일 때, 언제 DB 조회를 다시 실행할 것인가?" 
동작 : 사용자가 탭을 전환했다 복귀할 때(refetchOnWindowFocus), 네트워크가 재연결될 때(refetchOnReconnect) 등 트리거에 맞춰 재조회 격발.

3) retry (에러 재시도 정책) 
속성 : "요청이 실패했을 때 몇 번 더 재시도할 것인가?" 
동작 : 기본 3회. 지수 백오프(Exponential Backoff: 요청 간격을 점진적으로 늘림) 방식으로 서버 과부하를 방지하며 자동 복구 시도.

# 5. Mutation 이후 invalidation이 필요한 이유를 설명한다.

Mutation - CUD작업(`POST`, `PUT`, `DELETE`)을 성공했다고 해서, 프론트엔드 메모리에 이미 보관 중이던 기존 조회 캐시(GET)가 알아서 바뀌지 않는다.

```tsx
const mutation = useMutation({
  mutationFn: createPost,
  onSuccess: () => {
    // 'posts' 키를 사용하는 모든 캐시를 즉시 만료(stale) 처리하고, 화면에 활성화되어 있다면 백그라운드 재조회 격발
    queryClient.invalidateQueries({ queryKey: ['posts'] });
  },
});
```

- 프론트 수동 배열 조작(unshift)의 한계:
글 작성 후 posts.unshift(newPost)처럼 프론트에서 배열을 직접 조작하면, 서버 측 정렬 기준(ORDER BY), 페이징 번호 밀림 현상, DB 트리거로 계산되는 자동 컬럼값과 싱크가 깨지게 된다.

- invalidateQueries의 동작 방식
  1. 기존 캐시를 즉시 만료(stale) 상태로 마킹한다.
  2. 현재 화면에서 해당 데이터를 구독 중인 컴포넌트가 있다면, 즉각 백그라운드 refetch를 때려 원격 DB의 최신 결과로 화면을 덮어씌운다.

# 6. Optimistic Update의 장점과 rollback 위험을 이해한다.

1) 장점: 사용자 경험 극대화
  '좋아요', '북마크' 클릭 시 서버 응답(200~500ms)을 기다리지 않고, 캐시를 먼저 조작하여 화면을 즉각적으로 변경한다.

2) Rollback 위험: 상태 불일치(Inconsistency)
  백엔드에서 500 서버 에러, 세션 만료, DB Lock이 발생했는데 화면에만 '좋아요 완료' 상태가 유지되면 치명적인 거짓 정보가 된다.
  따라서 onMutate 시점에 수정 직전 스냅샷(previousData)을 반드시 보관하고, 실패 시 onError에서 강제 원복하는 코드가 필수적이다.

```tsx
useMutation({
  mutationFn: toggleLikeApi,

  // 1. 서버로 요청을 쏘기 직전에 실행
  onMutate: async () => {
    // 진행 중인 refetch 취소 (낙관적 결과 덮어쓰기 방지)
    await queryClient.cancelQueries({ queryKey: ['post', id] });

    // 롤백을 위한 기존 캐시 스냅샷 확보
    const previousPost = queryClient.getQueryData(['post', id]);

    // 캐시를 미리 직접 수정 (화면 즉시 반응)
    queryClient.setQueryData(['post', id], (old) => ({
      ...old,
      isLiked: !old.isLiked,
    }));

    return { previousPost }; // context로 전달
  },

  // 2. 서버 통신 실패 시 원상복구
  onError: (err, variables, context) => {
    queryClient.setQueryData(['post', id], context.previousPost);
  },

  // 3. 성공하든 실패하든 최종적으로 DB 최신 데이터와 동기화 보장
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['post', id] });
  },
});
```

# 7. useEffect + fetch + useState와 Query Library의 책임 차이를 설명한다.

과거 방식: useEffect + useState (명령형 직접 구현)
본질: 단순히 화면이 Paint된 직후 브라우저에서 네트워크 요청을 1회 실행하는 코드.
개발자가 직접 짊어져야 하는 책임
  1. isLoading, isError 상태 플래그를 건건이 선언하고 수동 관리.
  2. 빠른 화면 전환 시 메모리 누수 방지용 ignore 불리언 클린업 구현.
  3. 동일 데이터를 쓰는 컴포넌트가 화면에 여럿 존재할 때 발생하는 중복 호출(Deduplication) 방어.
  4. 컴포넌트가 언마운트되면 데이터가 날아가서 재진입할 때마다 로딩 스피너 재발생.

모던 방식: Query Library / TanStack Query (선언형 캐시 위임)
본질: 프론트엔드 컴포넌트와 원격 DB 사이에서 동작하는 '선언형 캐시 관리 계층'.
라이브러리가 전담하는 책임:
  1. 캐싱 & 가비지 컬렉션: 화면을 벗어나도 메모리에 보관하며, 미사용 후 일정 시간 뒤 자동 청소(gcTime).
  2. 중복 요청 병합: 동시에 여러 컴포넌트가 요청해도 네트워크 탭에는 1건만 발송.
  3. 백그라운드 동기화: 브라우저 포커스 복귀 시 사용자 모르게 최신 데이터로 동기화.
  4. 컴포넌트의 단순화: 컴포넌트는 "데이터를 어떻게 가져오고 유지할지" 고민할 필요 없이, "키 줄 테니 현재 상태 가져와서 화면 그려"라는 뷰 렌더링 본업에만 집중.
