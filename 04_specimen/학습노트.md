# Component Boundary를 책임과 변경 빈도 기준으로 나눌 수 있다.

- 단일 책임 (Responsibility)
1. 컴포넌트의 역할을 데이터 조회, UI 렌더링, 사용자 액션 처리 중 하나로 명확히 분리한다. 
2. 한 컴포넌트가 너무 많은 역할을 쥐고 있지 않도록 경계를 나눈다.

- 변경 빈도 (Change Frequency)
1. 자주 바뀌는 영역(입력 폼, 타이머 등)과 거의 변하지 않는 영역(본문, 정적 레이아웃)을 한 컴포넌트에 두지 않는다.
2. 잦은 상태 변화가 정적 UI까지 불필요하게 리렌더링시키지 않도록 하위 컴포넌트로 격리한다.

# Composition과 Props Drilling 해결 전략을 비교한다.

1. 컴포넌트 합성 (Composition) : 중간 컴포넌트에 데이터를 넘기지 않고, 완성된 JSX를 직접 꽂아 넣어 중간 의존성을 제거한다.

1) Children 패턴 (단일 슬롯): children을 활용해 중간 레이아웃은 껍데기만 제공하고 상위에서 조립.

```jsx 
// props drilling (안티패턴)
function Layout({ user }) {
  return (
    <div className="layout">
      <Header user={user} />
    </div>
  );
}

// children 패턴
function Layout({ children }: { children: React.ReactNode }) {
  return <div className="layout">{children}</div>;
}

// 사용할 때 (최상위에서 직접 주입)
<Layout>
  <Header user={user} />
</Layout>
```
2) Slot Props 패턴 (멀티 슬롯): headerLeft={<Logo/>}, headerRight={<Profile/>}처럼 JSX 자체를 여러 props로 분할 주입.

```jsx
// Header는 위치(Slot)만 잡아줌
function PageHeader({ left, right }: { left: React.ReactNode; right: React.ReactNode }) {
  return (
    <header className="flex justify-between">
      <div>{left}</div>
      <div>{right}</div>
    </header>
  );
}

// 상위에서 필요한 데이터 가진 컴포넌트를 조립해서 주입
<PageHeader 
  left={<Logo />} 
  right={<UserMenu user={user} />} 
/>
```

2. State 끌어내리기 (Colocation) : 관습적으로 최상위에 올려둔 State를 실제 그 데이터를 소비하는 최하단 컴포넌트 근처로 이동시킨다. 불필요하게 높은 곳에 있던 상태만 내려도 Drilling 자체가 사라짐.

3. 전역 상태 / Context API : 합성이나 Colocation으로 해결하기 어려울 정도로 트리가 깊고, 앱 전반에서 널리 쓰이는 데이터(로그인 유저, 테마, 다국어 설정 등)에 한해 도입한다.


# Context가 필요한 경우와 과한 경우를 판단한다.

1. 본질: Context는 '전체 방송 무전기'다.
   - 중간 컴포넌트를 건너뛰고 바로 전달해주지만, 값이 1개라도 바뀌면 이 무전기를 쥔(useContext) 컴포넌트는 전부 다시 렌더링된다.

2. 필요한 경우 => 가끔 바뀌고, 많은 곳에서 쓸 때
   - 테마 설정: 다크모드/라이트모드 (자주 안 바뀌는데 온 화면이 다 씀)
   - 로그인 정보: 유저 권한 및 프로필 (로그아웃 전까지 유지되며 여러 곳에서 조회)
   - 컴포넌트 내부 묶음: 드롭다운(Select) 내부에서 열림/닫힘 상태 공유할 때

3. 과한 경우 => 자주 바뀌거나, 굳이 필요 없을 때
   - 실시간 입력값: 검색창 타이핑, 타이머 등 (글자 칠 때마다 구독자 전체가 리렌더링되어 버벅거림)
   - 2~3단계 단순 전달: 조금 귀찮다고 Context 쓰면, 부품을 다른 곳에서 단독으로 재사용하기 어려워짐
   - 짬뽕 객체: 유저 정보와 장바구니를 한 Context에 묶어서, 장바구니만 바뀌어도 유저 보던 컴포넌트까지 다 리렌더링되는 경우

# Custom Hook이 단순 코드 재사용 이상의 어떤 역할을 하는지 설명한다.

1. View와 로직의 분리 (관심사의 분리)
   - 재사용 목적이 아니더라도, 컴포넌트에서 데이터 패칭/비즈니스 로직을 걷어내고 순수 UI 렌더링에만 집중하게 만든다.

2. 리액트 상태 생명주기(Stateful Logic)의 캡슐화
   - 일반 JS 유틸 함수와 달리 useState, useEffect 등 리액트 훅을 조합하여 이벤트 등록/해제, 상태 동기화 같은 복잡한 흐름을 하나로 묶어 관리한다.

3. 선언적 인터페이스 제공 (구현 은닉)
   - 내부의 복잡한 구현(API 통신, 로컬스토리지 동기화 등)을 숨기고, 쓰는 쪽에서는 직관적인 상태 값과 핸들러만 꺼내 쓸 수 있도록 캡슐화한다.

# Controlled / Uncontrolled 설계 trade-off를 이해한다.

1. 개념 차이 (Source of Truth)
   - Controlled (제어): 상태를 React State가 보유. 타이핑마다 onChange로 state 갱신 및 re-render.
   - Uncontrolled (비제어): 상태를 브라우저 DOM이 보유. 필요할 때 useRef나 Submit 이벤트로 DOM에서 직접 추출.

2. Trade-off
   - Controlled: 
     - 장점: 실시간 유효성 검사, 자동 포맷팅(전화번호 등), 입력값 연동 UI 처리가 매우 쉬움.
     - 단점: 타이핑마다 리렌더링 발생, 인풋 개수가 많아지면 성능 부담.
   - Uncontrolled:
     - 장점: 입력 시 리렌더링이 전혀 없어 성능 우수, 파일 첨부 인풋이나 단순 제출 폼에 가벼움.
     - 단점: 실시간 UI 상태 반영 및 외부에서의 값 조작이 까다로움.

3. 실무 판단 기준
   - 실시간 유효성 검증과 동적 인터랙션이 핵심이면 -> Controlled
   - 입력 필드가 방대하여 렌더링 최적화가 필요하거나 단순 제출용 폼이면 -> Uncontrolled (React Hook Form 등)

# Referential Equality와 re-render의 관계를 설명한다.

1. 핵심 개념
   - React는 props와 state의 변경 여부를 얕은 비교(Object.is, ===)로 판단한다.
   - 원시값은 값을 비교하지만, 객체/배열/함수는 내용이 같아도 '메모리 주소(참조)'가 다르면 변경된 것으로 인식한다.
```jsx
// 내용물이 아니라 메모리 주소(참조)를 비교함.
1 === 1                 // true
{ a: 1 } === { a: 1 }   // false (새로운 힙 메모리 할당)
(() => {}) === (() => {}) // false (새로운 함수 인스턴스)

```

2. 리렌더링 시 발생하는 현상
   - 컴포넌트 함수가 다시 실행되면, 내부의 객체/배열/함수는 매번 새로운 메모리 주소로 재생성된다.
   - 이로 인해 React.memo를 적용한 자식 컴포넌트라도 매번 새 props를 받았다고 판단하여 불필요하게 리렌더링된다.
   - useEffect/useMemo의 의존성 배열에 객체/함수가 들어가 있으면, 의도치 않은 훅 재실행이나 무한 루프를 유발한다.

```jsx
function ParentComponent() {
  const [count, setCount] = useState(0);

  // ParentComponent가 리렌더링될 때마다 새로운 메모리 주소 할당!
  const filterOptions = { category: 'tech' }; 
  const handleClick = () => console.log('click');

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>클릭</button>
      {/* ChildComponent를 React.memo로 감싸도, 참조 주소가 바뀌어 불필요하게 리렌더링됨 */}
      <ChildComponent options={filterOptions} onClick={handleClick} />
    </div>
  );
}
```

```jsx
function SearchBox() {
  const [keyword, setKeyword] = useState('');

  // 렌더링마다 새 객체 생성 (참조 주소 변경)
  const queryParams = { keyword };

  useEffect(() => {
    fetchData(queryParams);
    // keyword가 안 바뀌고 다른 state 때문에 컴포넌트가 다시 그려져도,
    // queryParams 객체의 주소가 매번 달라지므로 이 effect가 계속 불필요하게 재실행됨!
  }, [queryParams]);
}
```

3. 해결 전략
   - 참조 동일성을 보장하기 위해 useMemo(객체/배열 캐싱), useCallback(함수 캐싱)을 사용하여 렌더링 간 메모리 주소를 안정적으로 유지(Stabilize)시킨다.
```jsx

// 의존성이 바뀌지 않는 한, 리렌더링되어도 동일한 메모리 주소를 유지함
const filterOptions = useMemo(() => ({ category: 'tech' }), []);
const handleClick = useCallback(() => console.log('click'), []);
```

# React.memo, useMemo, useCallback을 언제 사용하지 않아야 하는지 판단한다.

1. 메모이제이션 비용 vs 재계산 비용
   - 메모이제이션은 공짜가 아니다. (메모리 점유, 의존성 비교 연산, 코드 복잡도 증가)
   - "다시 계산/렌더링하는 비용"이 "deps를 비교하고 캐싱하는 비용"보다 작다면 사용하지 않는 것이 이득이다.

2. 사용하지 않아야 하는 구체적 케이스
   - useMemo: 
     - 단순 산술 연산(a + b), 문자열 조합, 원시값 계산
     - 길이가 짧은 소규모 배열 가공(filter, map)
   - useCallback:
     - <button>, <input> 같은 일반 네이티브 HTML DOM에 전달하는 이벤트 핸들러
     - 자식 컴포넌트가 React.memo로 감싸져 있지 않은 경우 (어차피 자식이 리렌더링됨)
   - React.memo:
     - props가 매 렌더링마다 달라지는 컴포넌트 (비교 연산 비용만 낭비)
     - 내부 DOM 구조가 매우 단순하여 다시 그리는 비용이 거의 없는 컴포넌트
     - [props가 거의 고정됨] + [내부 렌더링 트리가 무거움] 두 조건이 동시에 맞을 때만 memo를 쓴다.

# Profiler로 병목을 먼저 측정한 뒤 최적화하는 절차를 익힌다.

1. 기본 원칙 : "측정하지 않은 최적화는 최적화가 아니라 그냥 코드 복잡도 증가다."
   - 추측으로 최적화하지 않는다. 반드시 React Profiler로 병목 컴포넌트와 원인을 수치로 측정한 뒤 작업한다.

2. 4단계 최적화 절차
   - 1단계 (기록): 개발자도구 Profiler 설정에서 "Record why each component rendered" 활성화 후 병목 인터랙션 녹화.
   - 2단계 (탐색): Flamegraph 차트에서 렌더링 소요 시간이 긴 주황색/노란색 컴포넌트 식별 (16ms 초과 여부 확인).
   - 3단계 (원인 파악): 해당 컴포넌트의 우측 패널에서 리렌더링 이유 확인 (부모 렌더링 때문인지, props 참조 변경 때문인지).
   - 4단계 (해결 및 검증): 
     - 원인에 맞게 상태 분리, React.memo, useCallback 등을 국소 적용.
     - 동일 액션을 재측정하여 렌더링 시간/횟수 감소를 수치로 검증 (개선 없으면 롤백).


# React Compiler가 수동 memoization 전략에 미치는 영향을 이해한다.

1. React Compiler의 역할
   - 빌드 타임에 컴포넌트 코드를 정적 분석하여, 값·객체·JSX 요소의 메모이제이션 처리를 컴파일러가 자동으로 주입한다.

2. 자동 memoization 도입으로 인한 개발 패턴의 변화
   - 수동 훅(useMemo, useCallback, React.memo) 직접 작성 불필요
   - 의존성 배열(deps) 관리 및 클로저 버그(Stale Closure) 스트레스 해소
   - 최적화 껍데기가 사라져 순수 비즈니스 로직과 UI 코드만 남아 가독성 향상

3. 개발자에게 요구되는 핵심 역량
   - 컴파일러가 안전하게 최적화할 수 있도록 "React의 규칙(순수 함수 원칙, 불변성 유지)"을 엄격히 지키는 코드를 작성해야 함.
   - 책임과 변경 빈도에 따른 컴포넌트 분리 같은 아키텍처적 설계는 여전히 개발자의 몫으로 남음.
