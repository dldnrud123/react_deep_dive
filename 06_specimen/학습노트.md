# 1. Server Component와 Client Component를 execution environment 관점에서 구분한다.
두 컴포넌트의 가장 근본적인 차이는 "코드가 어디서 평가(실행)되고, 브라우저 번들에 최종 포함되는가"에 있다.

1) Server Component (RSC, 기본값)
- 실행 위치: 오직 서버 환경(Node.js / Edge Runtime)에서만 실행된다.
- 번들 영향: 브라우저로 소스 코드가 아예 전송되지 않으므로 JS 번들 크기는 0 Byte다.
- 접근 자원: 서버 내부망의 DB 직접 쿼리, 파일 시스템(fs), 비공개 API 키 등 민감한 자원에 안전하게 붙을 수 있다.
- 제약 사항: 브라우저 런타임이 없기 때문에 'useState', 'useEffect' 같은 리액트 훅이나 'onClick' 같은 DOM 이벤트 핸들러는 사용할 수 없다.
- 결과물: HTML 문자열이 아니라, 리액트 가상 DOM 트리를 직렬화한 데이터 포맷인 RSC Payload 형태로 클라이언트에 전달된다.

2) Client Component ('use client')
- 실행 위치: 이름과 달리 브라우저 전용이 아니다. 초기 접속 시에는 서버에서 정적 HTML을 만드는 데 먼저 참여하고, 이후 브라우저로 번들이 내려가 런타임 환경에서 동작한다.
- 번들 영향: 컴포넌트 로직이 클라이언트 번들에 고스란히 포함되므로 다운로드 및 파싱 비용이 발생한다.
- 관리 대상: 버튼 클릭, 폼 입력 같은 사용자 인터랙션과 컴포넌트 내부의 휘발성 상태(useState)를 다룬다.
- 판단 기준: 화면에 데이터만 뿌려주는 정적 뷰라면 서버 컴포넌트로 두고, 사용자 인터랙션이나 브라우저 API가 반드시 필요한 말단(Leaf) 영역만 클라이언트 컴포넌트로 좁혀서 선언하는 것이 유리하다.

# 2. RSC와 SSR을 서로 다른 개념으로 설명할 수 있다.

둘 다 "서버"에서 돌아가니 얼핏 비슷해 보이지만, 해결하려는 문제(목적)와 최종 결과물의 포맷이 완전히 다르다.

1) SSR (Server-Side Rendering) : "초기 로딩 속도(FCP)와 SEO 최적화"
- 배경: SPA의 고질병인 초기 흰 화면(빈 div)을 없애기 위해 등장했다.
- 방식: 요청이 들어오면 서버에서 컴포넌트 트리를 실행해 "완성된 순수 HTML 텍스트 문자열"을 즉시 내려준다.
- 한계: 눈에는 화면이 바로 뜨지만, 브라우저가 화면을 구성하는 모든 컴포넌트의 JS 번들을 다운로드받고 Hydration(이벤트 바인딩)을 끝내기 전까지는 버튼을 눌러도 동작하지 않는다. 즉, JS 번들 사이즈 자체를 줄여주지는 못한다.

2) RSC (React Server Components) : "실행 위치 격리와 번들 사이즈 다이어트"
- 배경: 클라이언트가 굳이 알 필요 없는 무거운 비즈니스 로직과 라이브러리를 브라우저 번들에서 덜어내기 위해 등장했다.
- 방식: 서버 컴포넌트는 서버에서만 돌리고, 브라우저에는 컴포넌트 코드가 아닌 렌더링 결과(RSC Payload)만 전달한다.
- 차별점: 마크다운 파서나 날짜 포맷 라이브러리처럼 무거운 패키지를 서버에서만 돌리고 번들에서는 영구 배제할 수 있다.

**정리**  
- SSR은 "언제 완성된 HTML을 보여줄 것인가(렌더링 시점)"의 최적화다.
- RSC는 "어떤 코드를 브라우저 번들에서 제외할 것인가(실행 위치와 번들 격리)"의 아키텍처다.

# 3. Hydration이 무엇이고 언제 필요한지 설명한다.

서버가 렌더링한 정적 HTML 뼈대에 브라우저 측 리액트가 자바스크립트 로직과 이벤트 리스너를 결합하여 인터랙티브한 상태로 전환하는 과정이다.

1) Hydration의 동작 파이프라인
- Step 1 (서버): 컴포넌트를 정적 HTML로 렌더링하여 브라우저로 전송한다. 사용자는 JS 다운로드가 끝나기 전에도 화면을 볼 수 있다(Fast FCP).
- Step 2 (브라우저): 브라우저가 클라이언트 JS 번들을 다운로드하고 파싱/실행한다.
- Step 3 (Hydration): 리액트 런타임이 기존에 그려진 실제 DOM 트리를 탐색하면서 가상 DOM과 1:1로 매핑하고, 'onClick' 같은 이벤트 리스너와 'useState' 메모리 상태를 연결한다.
- Step 4 (인터랙션 활성화): 바인딩이 완료된 시점부터 사용자의 클릭이나 입력에 즉각 반응하기 시작한다(TTI 달성).

2) Hydration이 필요한 조건
- 사용자 인터랙션 처리: 버튼 클릭, 모달 열기, 폼 입력 등 DOM 이벤트 리스너 바인딩이 필수적인 컴포넌트.
- 컴포넌트 내부 상태 추적: 'useState', 'useReducer'처럼 브라우저 메모리에 상주하며 UI 변화를 유발하는 상태가 존재하는 경우.
- 브라우저 사이드 이펙트: 'useEffect' 같은 라이프사이클 훅 실행이나 Web API('window', 'localStorage') 접근이 필요한 경우.

3) Server Component 관점에서의 혁신
- 순수 Server Component는 이벤트 리스너도 없고 브라우저 상태도 갖지 않는다.
- 따라서 서버 컴포넌트 영역은 브라우저에서 Hydration 단계를 완전히 건너뛴다.
- 브라우저는 정적 UI 영역에 대해 DOM을 순회하며 리스너를 붙이는 불필요한 JS 연산을 하지 않으므로, 기기 성능에 구애받지 않고 초기 구동 속도가 대폭 향상된다.

4) 주의점 (Hydration Mismatch)
- 서버에서 렌더링한 초기 HTML 마크업과 브라우저가 Hydration 직전 첫 번째로 계산한 가상 DOM 구조가 불일치할 때 발생한다.
- 서버와 클라이언트의 타임존 차이('new Date()'), 렌더링 분기('typeof window !== 'undefined''), 잘못 중첩된 HTML 태그(예: '<p>' 태그 안의 '<div>') 등으로 인해 발생하므로 초기 렌더링 결과가 양쪽 환경에서 동일하도록 보장해야 한다.

* 단순 이벤트 바인딩과의 차이점
- 실제 DOM과 가상 DOM(Fiber)의 1:1 링크:
  서버가 만들어둔 실제 DOM 엘리먼트를 파괴하지 않고 순회하면서, 리액트 내부의 가상 DOM 노드(Fiber)와 1:1 포인터를 연결한다. 이 연결이 있어야 추후 상태 변경 시 어느 DOM을 수정할지 추적할 수 있다.
- 훅(Hook) 메모리 슬롯 초기화:
  컴포넌트 함수를 실행하여 'useState'의 초기 상태값을 브라우저 메모리에 할당하고, 'useRef'를 실제 DOM 노드와 연결하며, 'useContext' 구독 관계를 형성한다.
- 이벤트 위임(Event Delegation) 등록:
  개별 DOM 엘리먼트마다 'addEventListener'를 일일이 부착하지 않는다. 리액트는 루트 컨테이너('div#root') 레벨에서 이벤트를 위임받아 처리하므로, Hydration 시점에는 내부 합성 이벤트(SyntheticEvent) 디스패처에 핸들러를 등록한다.
- 라이프사이클 이펙트 스케줄링:
  DOM 연결과 상태 초기화가 완료된 직후, 브라우저 마운트 시점에 동작해야 하는 'useEffect' 및 'useLayoutEffect' 콜백을 실행 큐에 올려 즉각 트리거한다.

**정리**  
이벤트 리스너 바인딩은 Hydration의 일부 결과일 뿐이며, 본질은 "서버가 렌더링한 정적 DOM을 리액트의 가상 DOM 관리 체계(Fiber) 안으로 편입시켜 완벽한 반응형 상태로 만드는 작업"이다.

# 4. use client가 파일 하나의 실행 위치만 뜻하는 것이 아니라 boundary를 만든다는 점을 이해한다.

'use client'는 단순한 런타임 플래그가 아니라, 번들러(Webpack, Turbopack)에게 서버와 클라이언트 모듈 사이의 경계선(Client Boundary)을 선언하는 지시어다.

1) Client Boundary와 종속성 전파 (Cascade)
- 진입점 역할: 최상단에 'use client'가 선언된 모듈은 **서버 전용 코드 공간에서 클라이언트 번들 공간로 넘어가는 진입점**이 된다.
- 하위 모듈 자동 편입: 해당 파일에서 import하는 모든 하위 컴포넌트, 서드파티 라이브러리, 유틸리티 함수는 파일 내부에 'use client'를 명시하지 않더라도 전부 클라이언트 JS 번들에 강제로 포함된다.
- 즉, 'use client'는 파일 단 한 개에만 국한되는 것이 아니라 그 모듈이 뻗어나가는 **하위 의존성 트리 전체를 클라이언트 영역으로 감싸는 경계선**을 긋는 것이다.

2) 아키텍처 관점에서의 주의점 (상단 오염 방지)
- 트리 상단 선언 금지: 페이지 루트나 상위 레이아웃 컴포넌트에 무심코 'use client'를 선언하면, 하위의 모든 자식 컴포넌트가 클라이언트 번들로 빨려 들어가 RSC의 번들 절감 효과가 무력화된다.
- 말단 격리(Move to Leaves) 원칙: 'use client'는 이벤트 핸들러나 상태 관리가 반드시 필요한 가장 말단(Leaf) 컴포넌트로 최대한 밀어넣어 번들 크기를 최소화해야 한다.

```

[Server Component: Page.tsx] (서버 전용, 0 Byte)
  │
  └── <Header /> (RSC)
  │
  └── <Counter /> ('use client' 선언 지점 -> 여기서 경계선 발생!)
        │
        ├── import <Button />  (use client 안 적어도 Client Component로 강제 편입)
        ├── import <Icon />    (use client 안 적어도 Client 번들에 포함)
        └── import formatUtil  (use client 안 적어도 클라이언트 번들 용량 차지)

```

3) Client Component 내부에 Server Component를 배치하는 법 (Slot / Children 패턴)
- 직접 import의 한계: Client 파일 내부에서 Server Component를 직접 import하면, 해당 컴포넌트 역시 Client Component로 강제 격하되어 번들에 포함된다.
- children props 활용: Server Component가 부모 역할을 맡고, Client Component에 Server Component를 children 또는 별도 props로 주입하는 구조를 사용한다.

```tsx
// Server Component (Page.tsx)
import ClientModal from './ClientModal';       // Client Component
import ServerDataList from './ServerDataList'; // Server Component (DB 직접 조회)

export default function Page() {
  return (
    <ClientModal>
      {/* 서버에서 이미 렌더링(RSC Payload)된 결과를 props(children) 슬롯에만 끼워 넣음 */}
      <ServerDataList/>
    </ClientModal>
  );
}

```

# 5. Client Component가 필요한 조건을 판단한다.
모던 리액트(App Router) 아키텍처의 기본 원칙은 **"기본값은 Server Component로 두고, 브라우저 환경이 강제되는 예외 상황에서만 Client Component로 격리한다"**이다.

1) Client Component 전환이 필수적인 3대 조건
아래 항목 중 단 하나라도 필요하다면 ''use client'' 경계를 선언해야 한다.

- DOM 이벤트 리스너가 필요한 경우:
  'onClick', 'onChange', 'onSubmit', 'onDrag' 등 사용자의 직접적인 브라우저 입력 및 인터랙션을 감지해야 할 때.
- 브라우저 상태 및 생명주기 훅을 사용할 때:
  'useState', 'useReducer'를 통한 컴포넌트 내부 휘발성 상태 관리, 'useEffect'를 통한 DOM 마운트 후 부수 효과 처리.
- 브라우저 전용 Web API에 접근할 때:
  'window', 'document', 'localStorage', 'sessionStorage', Geolocation API, Web Audio 등 서버(Node.js) 런타임에 존재하지 않는 브라우저 객체를 참조할 때.

2) Server Component로 유지해야 하는 케이스 
- 데이터 페칭 및 백엔드 리소스 접근:
  DB 쿼리 실행, 비공개 API Key를 활용한 외부 연동, 백엔드 마이크로서비스 호출 등은 모두 Server Component에서 처리하는 것이 보안 및 번들 관점에서 우월하다.
- 정적 뷰 및 마크업 레이아웃:
  단순 텍스트 렌더링, 정적 이미지/SVG 아이콘, CSS 스타일링(Tailwind CSS 등)은 클라이언트 JS가 개입할 이유가 없으므로 서버에 둔다.
- URL 파라미터 기반의 정적 뷰 전환:
  URL의 'params'나 'searchParams'를 읽어 데이터를 다르게 조회하는 작업은 Server Component 자체에서 완결 가능하다.

3) 실무 적용 의사결정 흐름도 (Decision Flow)

```
[컴포넌트 작성 시작 (Default: Server Component)]
│
▼
사용자 이벤트(onClick, onChange 등) 처리가 필요한가?
├─ [Yes] ──> Client Component ('use client')
└─ [No]  ──┐
▼
useState, useEffect 등 클라이언트 훅이 필요한가?
├─ [Yes] ──> Client Component ('use client')
└─ [No]  ──┐
▼
window, localStorage 등 브라우저 Web API를 쓰는가?
├─ [Yes] ──> Client Component ('use client')
└─ [No]  ──> Server Component 확정 (번들 0 Byte 달성)

```

4) 컴포넌트 분리 실전 패턴 (Leaf 격리)
- 나쁜 예: 화면 상단에 상태가 하나 필요하다고 페이지 전체(page.tsx)를 'use client'로 선언하여 하위 전체를 클라이언트 번들로 전락시키는 구성.
- 좋은 예: 페이지 전체는 데이터 페칭을 전담하는 Server Component로 유지하고, 인터랙션이 발생하는 가장 말단 요소(예: <LikeButton />, <SearchBar />, <DropdownMenu />)만 별도 파일로 쪼개어 Client Component로 격리하는 구성.

# 6. Server Component에서 데이터를 가져오는 장점을 설명한다.

과거 SPA의 클라이언트 데이터 페칭(useEffect + fetch) 방식과 비교했을 때, 네트워크 효율성, 보안, 번들 최적화 관점에서 근본적인 아키텍처적 우위를 가진다.

1) 네트워크 왕복 지연의 극적인 단축
- 물리적 거리의 한계 극복:
  기존 방식은 브라우저가 공용 인터넷망을 거쳐 백엔드 API 서버로 요청을 보내므로 네트워크 지연(RTT)이 크다.
- 데이터센터 내부망(LAN) 활용:
  Server Component는 웹 서버와 DB 또는 내부 마이크로서비스가 같은 데이터센터나 초고속 사설 네트워크로 연결된 환경에서 실행된다. 수십~수백 밀리초가 걸리던 원격 API 왕복 비용을 1~5ms 단위의 내부망 통신으로 단축시킬 수 있다.

2) Zero-Bundle-Size 데이터 가공
- 무거운 종속성의 클라이언트 번들 제외:
  데이터를 가공하기 위해 필요한 무거운 서드파티 라이브러리(예: 마크다운 렌더러, 날짜 변환 라이브러리, 데이터 필터링 유틸 등)를 서버 환경에서만 실행할 수 있다.
- 순수 렌더링 결과만 전달:
  브라우저에는 라이브러리 소스 코드가 아닌, 가공이 완료된 UI 렌더링 결과(RSC Payload)만 전송되므로 클라이언트 JS 번들 크기를 0 Byte로 유지할 수 있다.

3) 강력한 보안성과 아키텍처 단순화
- 비공개 자원의 안전한 사용:
  DB 커넥션 스트링, 비공개 인증 토큰, 외부 연동 Secret Key를 클라이언트에 전혀 노출하지 않고 서버 메모리 안에서 안전하게 사용한다.
- 불필요한 중간 API 엔드포인트 제거:
  단순히 화면 조회를 위해 백엔드와 프론트엔드 사이에 GET REST API를 일일이 만들 필요 없이, 서버 컴포넌트 내부에서 DB나 ORM을 통해 직접 쿼리(Direct Access)를 수행할 수 있다.

4) 선언적이고 직관적인 비동기 코드
- 보일러플레이트 제거:
  과거 클라이언트 페칭에서 필수로 요구되던 'useState'(로딩, 에러, 데이터 관리)와 'useEffect' 생명주기 관리 코드가 완전히 사라진다.
- async/await 직접 사용:
  컴포넌트 함수 자체를 비동기(async)로 선언하고 상단에서 직관적으로 데이터를 가져와 그대로 JSX에 바인딩할 수 있어 코드의 가독성과 유지보수성이 크게 향상된다.


# 7. Streaming / Suspense가 waterfall과 UX에 미치는 영향을 이해한다.

전통적인 서버 렌더링의 고질적인 'All-or-Nothing' 병목을 해결하고, 점진적 렌더링(Progressive Rendering)을 통해 사용자 체감 로딩 속도를 극대화하는 아키텍처다.

1) 전통적 서버 사이드 렌더링의 병목 (All-or-Nothing)
- 블로킹 현상:
  페이지 내 대부분의 데이터가 10ms 만에 준비되더라도, 단 하나의 느린 쿼리(예: 추천 알고리즘 연산 3초 지연)가 존재하면 서버는 전체 HTML 전송을 대기해야 한다.
- 사용자 경험 저하:
  브라우저는 서버로부터 단 1바이트의 응답도 받지 못하므로, 사용자는 3초 동안 흰 화면(Blank Screen)을 마주하게 된다.

2) Streaming + Suspense의 점진적 전송 구조
HTTP의 청크 전송(Chunked Transfer Encoding) 기술을 활용하여, 비동기 작업의 지연 영역을 격리하고 렌더링 결과를 스트림 형태로 쪼개어 브라우저에 보낸다.

```tsx
// Page.tsx (Server Component)
export default function Page() {
  return (
    <div>
      <Header/> {/* 즉시 렌더링되어 브라우저로 1차 전송 */}
      <MainPost/> {/* 빠른 본문 쿼리 완료 즉시 렌더링 */}

      {/* 3초 지연이 발생하는 무거운 영역은 Suspense로 격리 */}
      <Suspense fallback="{<ProductSkeleton"/>}>
        <SlowRecommendedProducts/>
      </Suspense>
    </div>
  );
}

```
* 'fallback'은 모든 JSX 태그에 공통으로 존재하는 범용 prop이 아니라, **리액트 내장 특수 컴포넌트(Suspense 등)에서 대체 UI를 주입받기 위해 규격화된 전용 prop**이다.
