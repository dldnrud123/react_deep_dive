
## 주제 : 동일 데이터를 Local State, URL State로 각각 구현하고 trade-off 비교

[실험방법]
1. Local State 변경 버튼을 눌러 값 변경
2. URL State 변경 버튼을 눌러 값 변경 
3. 새로고침 후 '선택된 탭'에 표시된 값 확인
4. url을 복사한 후 페이지 이동하여 '선택된 탭'에 표시된 값 확인
5. 뒤로가기 또는 앞으로가기 후 '선택된 탭'에 표시된 값 확인 

[실험결과]
- 새로고침 : Local State 값 초기화, URL State 값 유지
- url공유 : Local State 값 초기화, URL State 값 유지
- 뒤로가기 or 앞으로가기 
  -- URL State : 브라우저 히스토리 이벤트(popstate)와 연동되어 이전 탭으로 정확하게 복원 및 변경됨.
  -- Local State : 
        1. URL 쿼리만 바뀐 SPA 환경에서는 컴포넌트가 언마운트되지 않아 기존 메모리 값이 그대로 유지됨.
        2. 외부 페이지 이동 후 뒤로가기로 복귀한 경우, 최신 브라우저의 BFCache(Back-Forward Cache)가 JS 메모리 스냅샷을 보존해 두었기 때문에 
           로컬 값이 유지되어 나타남.

[결론]

URL State: URL 상의 Query String 형태로 데이터를 관리함. 
           새로고침 유지, 브라우저 히스토리 제어, 링크 공유가 필수적인 상태(검색, 필터, 페이지네이션)에 반드시 채택해야 함.
           공유와 복원에 유리하지만 문자열 직렬화 비용과 URL 길이 제한이 있음.

Local State: 컴포넌트 내부 힙 메모리에서만 관리되므로 새로고침이나 공유 시 휘발됨. 
             화면 안에서만 소모되는 일회성 UI 상태(모달, 폼 입력 중 데이터)에 적합함.
             객체/배열 등 복잡한 데이터 처리가 가볍지만 영속성이 없음.
