#  State Snapshot을 설명할 수 있다.

'State Snapshot'이란 동일 랜더링 시점의 값이다.
변수처럼 변하지 않고, 컴포넌트라는 함수자체에 들어오는 인자값이라고 할 수 있다. 

- 아래 예시1 코드를 확인해보자

(예시1)

```jsx

function setStateA(stateA){
  let num = 0;
  num = stateA + 1;
  num = stateA + 1;
  num = stateA + 1;

  return num;
}

function setStateB(stateB){
  let num = stateB;
  num = num + 1;
  num = num + 1;
  num = num + 1;

  return num;
}

```
스코프를 보면 클로저에 의해서 내부에서만 동작한다는 것을 알 수 있다.

- 아래 예시2 코드를 확인해보자

(예시2)
``` jsx
function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    for (let i = 1; i <= 4; i++) {
      setCount(count + 1);
      setTimeout(() => {
        console.log("count:", count);
      }, 4000);
    }
  };

  return <button onClick={handleClick}>클릭</button>;
}
```

- 4초 후에 '0'이 찍힌다 -> 해당 snapshot 시점에는 state는 '0' 이기 때문에.

#  Update Queue와 Batching의 관계를 설명할 수 있다.
- Update Queue : 대기열 큐에 작업이 올라가는 것 (현재의 state snapshot 기준) <-> DB의 query
- Batching : 대기열 큐의 작업을 실행 하는 것 <-> DB의 commit

``` sql
START TRANSACTION;  -- 랜더링
UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- Update Queue 1
UPDATE accounts SET balance = balance + 100 WHERE id = 2; -- Update Queue 2
COMMIT; -- 이 순간 데이터 파일에 확정 기록 -- Batching

```


- rollback(롤백)은 없을까?
아래 낙관적 업데이트를 진행 하거나 react19의 useOptimistic 사용.

``` jsx
const handleLike = async () => {

  const previousLiked = isLiked;
```

#  Functional Update가 필요한 상황을 판단할 수 있다.

setCount(count + 1); 을 여러번 하게되면 현재 스냅샷 기준의 count에 + 1을 하는 것과 같은 연산이기 때문에


```jsx 
const [count, setCount] = useState(0);

setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
```
위 처럼 수행해도 결과값은 1이 나올것이다.

이것의 결과값이 '3'이 되길 기대했다면 소스는 아래처럼 작성되어야한다.
```jsx 
const [count, setCount] = useState(0);

setCount(prev => prev + 1);
setCount(prev => prev + 1);
setCount(prev => prev + 1);

```

#  State Preservation / Reset을 Component Identity 관점에서 설명할 수 있다.

- component Identity

리액트는 컴포넌트의 정체성을 UI 트리 상의 위치(Position), 컴포넌트 타입(Function/Tag), 그리고 key 3가지의 조합으로 식별한다. 
state는 컴포넌트 함수 내부가 아니라 리액트 엔진의 대응되는 Fiber 노드에 저장된다.

- state의 보존 (preservation)

재렌더링 시 동일한 트리 위치에서 컴포넌트의 타입과 key가 이전 렌더링과 동일하다면, 
리액트는 동일한 컴포넌트 인스턴스로 판단하여 기존 Fiber 노드를 재사용하고 State를 그대로 유지한다.

- state의 초기화 (reset)

컴포넌트의 위치가 변경되거나, 타입이 바뀌거나, key 값이 변경되면 리액트는 Identity가 달라진 것으로 판단한다. 
기존 Fiber 노드를 메모리에서 파괴(Unmount)하고 새로운 노드를 생성(Mount)하므로 State는 완전히 초기화된다.


#  Source of Truth와 Derived State를 구분한다.

- source of truth (원천소스) : 소스의 원본 그 자체.
- derived state (파생상태) : 원천 소스로부터 단순 계산/가공을 통해 즉시 얻을 수 있는 값.

(예시 1) 우리가 가독성을 위해서 쓰는 코드. 

```jsx
let goodsAmount = 7000;
let deliveryAmount = 3000;
let totalAmount = goodsAmount + deliveryAount;

```


(예시 2) 리액트에서 useState를 이런식으로 쓸 경우 : 매번 갱신을 해줘야하기 때문에 안티패턴에 해당.
```jsx
function OrderSheet() {
  // Source of Truth (원천 데이터)
  const [goodsAmount, setGoodsAmount] = useState(7000);
  const [deliveryAmount, setDeliveryAmount] = useState(3000);

  // 💥 재앙의 시작: 계산하면 나오는 값을 별도 상태로 선언
  const [totalAmount, setTotalAmount] = useState(10000);
  

  // 할인 쿠폰을 적용해서 상품 금액이 5000원으로 바뀌는 핸들러
  const applyCoupon = () => {
    const nextGoodsAmount = 5000;
    
    setGoodsAmount(nextGoodsAmount);
    
    // 개발자가 일일이 동기화 연산 코드를 직접 작성해야 함!
    // 만약 실수로 이 줄을 빼먹으면 상품가는 5000원인데 총액은 여전히 10000원이 찍히는 무결성 붕괴 발생
    setTotalAmount(nextGoodsAmount + deliveryAmount);
  };

  // 아래(주석)처럼 사용해야 매번 갱신을 안해줘도 됨.
  // const totalAmount = goodsAmount + deliveryAmount;

  // const applyCoupon = () => {
  //   setGoodsAmount(5000); 
  // };

  return (
    <div>
      <p>상품 금액: {goodsAmount}원</p>
      <p>배송비: {deliveryAmount}원</p>
      <p>총 결제 금액: {totalAmount}원</p>
      <button onClick={applyCoupon}>2,000원 할인 적용</button>
    </div>
  );
}
```


#  Duplicated State의 문제를 찾을 수 있다.

Source of Truth으로 Derived State값을 도출해낼 수 있다면, 
굳이 Duplicated state를 만들어 낼 필요가 없다. 

가독성을 좋게 만들겠다고 useState를 하나 더 파는 순간:
"가독성"을 얻는 게 아니라, 두 상태 사이의 "동기화 책임(Sync Overhead)"을 개발자가 온전히 떠안게 돼.
한쪽은 갱신됐는데 다른 쪽은 옛날 스냅샷을 쥐고 있는 데이터 불일치(Stale State) 버그가 생김.

```jsx

function UserNameForm() {
  const [firstName, setFirstName] = useState('우경');
  const [lastName, setLastName] = useState('이');

  const [fullName, setFullName] = useState('이우경');
  
  //아래 처럼 적용
  //const fullName = lastName + firstName;

  const handleLastNameChange = (e) => {
    const newLastName = e.target.value;
    setLastName(newLastName);

    // 개발자가 수동으로 동기화 로직을 계속 신경 써야 함
    // 만약 실수로 이 줄을 빼먹거나 오타를 내면 화면에 성은 바뀌었는데 풀네임은 안 바뀜!
    setFullName(newLastName + firstName);
  };

  return (
    <div>
      <input value={lastName} onChange={handleLastNameChange} />
      <input value={firstName} onChange={(e) => setFirstName(e.target.value)} />
      
      {/* firstName 인풋만 바꾸면 fullName이 안 바뀌는 데이터 불일치 버그 발생 */}
      <p>전체 이름: {fullName}</p>
    </div>
  );
}
```


#  State Colocation과 State Ownership을 설계할 수 있다.

State Colocation : state값을 선언하는 위치
State Ownership : state를 가지는 소유권, 어떤 conponent에 소유되는지 권한.

```jsx
function UserManagementPage() {
  // SearchInput에서만 쓰는 검색어 상태를 왜 최상위 페이지에 선언했는가
  const [keyword, setKeyword] = useState(""); 

  return (
    <div>
      {/* 타이핑할 때마다 setKeyword 실행 */}
      <SearchInput keyword={keyword} onChange={setKeyword} />
      
      {/* 검색 버튼 누르지도 않았는데, 부모가 재랜더링 되어 타이핑 1글자마다 무거운 표가 통째로 다시 그려짐 */}
      <VeryHeavyTable />
    </div>
  );
}
```

1. 단독으로 사용되는 state의 경우, 해당 컴포넌트로 넣어 소유권을 최대한 말단 컴포넌트로 부여하기위해 Colocation 해준다.
2. 2개 이상의 컴포넌트에서 state를 사용할 경우, 그 둘의 가장 가까운 공통 부모로 상태를 끌어올려준다 (Lifting State Up)


#  Local / URL / Global Client / Server State를 구분할 수 있다.

Local State  : 모달 띄우기 같은 1회용 UI (useState)
URL State    : 새로고침 시 지워지면 안됨, RequestQuery (useSearchParams)
Global State : 다크모드 같은 사이트 전체 UI 설정이면, 전역에서 사용하는 state (zustand)
Server State : DB에서 가져온 데이터면 (React Query,TanStack Query)
