# 1. Server Component Data Fetching 흐름을 설명한다.

전통적인 SPA의 클라이언트 페칭(useEffect)이 가진 워터폴(Waterfall) 문제를 해결하고, 백엔드 단에서 데이터를 렌더링에 직접 꽂아 넣는 아키텍처다.

```tsx 

// Server Component (기본값)
import { db } from '@/lib/db';

export default async function UserProfile({ params }) {
  // 1. 서버 환경이므로 DB 다이렉트 쿼리 가능 (중간 API 엔드포인트 불필요)
  const user = await db.user.findUnique({ 
    where: { id: params.id } 
  });

  // 2. 데이터가 채워진 상태로 완성된 UI(RSC Payload)를 클라이언트로 전송
  return (
    <div className="profile-card">
      <h1>{user.name}</h1>
      <p>{user.email}</p>
    </div>
  );
}

```

1) 패칭(Fetching) 파이프라인의 단선화
- 기존 방식: 브라우저가 빈 화면 로드 -> JS 실행 -> useEffect로 API 호출 -> 서버 응답 대기 -> 상태(State) 업데이트 후 UI 재렌더링. (네트워크 왕복 2회 이상 발생)
- Next.js (App Router) 방식: 서버 컴포넌트 자체가 비동기(async) 함수로 동작. 컴포넌트 렌더링 단계에서 DB나 내부 API를 즉시 Await로 찌른 뒤, 데이터가 바인딩된 완성된 HTML(RSC Payload)을 브라우저로 한 번에 내려보낸다.

2) 아키텍처적 이점
- 브라우저 자원 절약: 클라이언트 측에 로딩 상태(isLoading)나 에러 처리 상태를 관리하기 위한 JS 코드가 전혀 필요 없다.
- PHP/JSP와의 유사성: 뷰(View)를 그리기 전 서버에서 DB를 먼저 조회해 HTML을 완성하던 전통적 방식의 장점을 리액트 생태계로 가져온 형태다. 단, 리액트의 컴포넌트 모델과 완벽히 통합되어 동작한다.

# 2. Server Action과 Route Handler의 책임과 선택 기준을 비교한다.

둘 다 "서버에서 실행되는 로직"이지만, 호출 주체와 사용 목적에 따라 완전히 다른 도구다. (mutation 일때만 해당)

1) Server Action : "내부 UI와 DB 간의 직접적인 상호작용 (Mutation)"
- 목적: 폼 전송, 버튼 클릭(좋아요 등)을 통해 DB 데이터를 삽입/수정/삭제할 때 사용한다.
- 특징: API 엔드포인트(URL)를 개발자가 직접 만들 필요가 없다. 클라이언트 컴포넌트에서 서버 액션 함수를 그냥 'import'해서 실행하면, Next.js가 내부적으로 RPC(원격 프로시저 호출) 통신을 알아서 처리한다.
- 비유: 과거 PHP 시절, 뷰 폼에서 던진 데이터를 받아 처리하던 `*_action.php`의 모던 리액트 버전이다.

2) Route Handler : "외부 시스템과의 통신 및 범용 API (REST)"
- 목적: 순수한 RESTful API 엔드포인트가 필요할 때 사용한다. (예: `/api/users`)
- 특징: 외부 서비스(결제 모듈 웹훅, 모바일 앱 클라이언트, 다른 백엔드 서버)가 내 서버로 요청을 보낼 때 열어주는 표준 HTTP 출입구다.
- 비유: AJAX 요청만 전담 처리하던 `ajax.*.php`나 외부 연동용 별도 API 스크립트와 역할이 같다.

**정리**
- 재활용없이 해당 시스템에서만 리액트 화면에서 버튼 눌러 DB를 바꾼다? -> **Server Action**
- 웹훅 또는 재활용이 필요하여 API 엔드포인트로 만들어서 해당 엔드포인트에 접근하여 동작해야한다? -> **Route Handler**

# 3. Client Validation과 Server Validation의 역할을 구분한다.

클라이언트와 서버 양단에서 유효성 검사를 하는 것은 중복이 아니라 '이중 방어 체계'다.

1) Client Validation (UX 중심 방패)
- 목적: 사용자의 입력 실수에 대해 **가장 빠른 피드백**을 제공하는 것.
- 특징: 서버까지 네트워크 요청이 가기 전에 브라우저단에서 즉각 차단하여 불필요한 서버 리소스 낭비를 막는다. (예: 비밀번호 8자리 미만 입력 시 즉시 빨간색 경고 표시)
- 한계: 자바스크립트를 끄거나, Postman 같은 도구로 API를 직접 찌르면 쉽게 뚫린다.
- 예시 : 이메일 정규식, 비밀번호 자리수, 필수값 누락 등

2) Server Validation (최종 보안 방어선)
- 목적: 악의적 접근이나 비정상적인 데이터 파편이 **DB에 침투하는 것을 원천 차단**하는 것.
- 특징: 클라이언트에서 무슨 데이터를 보내든 "절대 믿지 않는다(Zero Trust)"는 전제하에 설계된다. Zod 같은 스키마 검증 라이브러리를 사용해 타입과 제약조건을 서버에서 한 번 더 깐깐하게 검사한다.
- 예시 : 잔고 부족 여부, 중복 아이디 존재 여부

# 4. Server-only 코드와 secret 관리 원칙을 이해한다.

Next.js 환경에서는 하나의 프로젝트 안에 클라이언트 코드와 서버 코드가 혼재하므로, 보안 키나 DB 접근 로직이 브라우저로 유출되지 않도록 철저히 통제해야 한다.

1) Secret 환경변수 관리 (`.env`)
- 서버 전용 변수: `DATABASE_URL`, `API_SECRET_KEY` 등은 서버에서만 접근 가능하다. 클라이언트 번들에서는 'undefined'로 평가된다.
- 퍼블릭 변수: 이름 앞에 `NEXT_PUBLIC_`을 붙인 변수만 브라우저 번들에 포함된다. (예: 카카오 맵 API 퍼블릭 키)
- 주의 사항 : DB 접속 문자열, AWS Secret Key, 결제 승인 비공개 키 등 시스템 권한을 쥔 모든 값은 절대로 NEXT_PUBLIC_을 붙이지 않는다.

2) `server-only` 패키지 활용
- 개념: 파일 최상단에 `import 'server-only'`를 선언하여 해당 파일이 "무조건 서버 환경에서만 실행되어야 함"을 강제한다.
- 효과: 만약 클라이언트 컴포넌트('use client')에서 실수로 DB 접속 객체나 서버 유틸리티 파일을 import하게 되면, 실행 전 빌드(Build) 단계에서 즉각 에러를 발생시켜 휴먼 에러를 원천 차단한다.


```tsx

// lib/db.ts
import 'server-only'; // 빌드 타임 가드 설치

import { PrismaClient } from '@prisma/client';
export const db = new PrismaClient();

```

# 5. Presentation / Application / Data Access 책임 분리를 경험한다.

실무에서 유지보수성을 높이고 스파게티 코드를 방지하기 위해 코드를 역할(Role) 단위로 3단계로 쪼개는 아키텍처 패턴이다.

1) Presentation Layer (표현 계층 / View)
- 역할: UI 컴포넌트 렌더링 및 사용자 이벤트(클릭, 입력) 수신.
- 위치: Server Component (`Page.tsx`) 및 Client Component (`Form.tsx`, `Button.tsx`).
- 특징: "어떻게 생겼는가"와 사용자 인터랙션 감지만 관여한다. 내부에서 SQL을 직접 치거나 복잡한 연산을 하지 않고, 이벤트 발생 시 Application 계층을 호출해 결과 뷰만 갱신한다.

2) Application Layer (응용 계층 / Service or Action)
- 역할: Server Action 또는 서비스 함수가 위치하는 곳. 업무 규칙(비즈니스 로직) 수행, 권한 검사(Auth), 2차 Server Validation을 총괄한다.
- 위치: Server Action 파일 (`actions/postActions.ts`) 또는 서비스 모듈 (`services/postService.ts`).
- 특징: 시스템의 핵심 두뇌 역할을 한다. 뷰에서 받은 데이터를 Zod 등으로 2차 검증하고 권한을 체크한 뒤 Data Access 계층으로 넘기며, 반대로 DB 데이터를 뷰 규격에 맞게 가공하여 전달한다.

3) Data Access Layer (데이터 접근 계층 / Model or Query)
- 역할: Prisma, Drizzle, Querydsl, Raw SQL 등을 이용해 실제 물리 DB나 외부 API와 통신하여 데이터를 영속화(CRUD)하는 영역.
- 위치: 쿼리 전용 파일 (`queries/post.ts`) 또는 리포지토리 (`repositories/postRepository.ts`).
- 특징: 순수하게 데이터 입출력만 담당한다. 비즈니스 규칙(할인율, 권한 등)을 전혀 모르며, 웹 환경(Request, Response, Session)에 종속되지 않는 순수 함수 형태로 작성되어 DB 교체나 테스트가 용이하다.

**정리**
- Presentation: 화면과 이벤트를 그린다 (UI)
- Application: 권한, 검증, 비즈니스 흐름을 제어한다 (로직)
- Data Access: 순수하게 DB만 읽고 쓴다 (쿼리)

# 6. 작은 프로젝트에서 abstraction이 과해지는 지점을 판단한다.

계층 분리와 디자인 패턴은 유지보수를 위한 도구일 뿐 절대적인 규칙이 아니며, 프로젝트 규모에 맞지 않는 과도한 추상화(Over-abstraction)는 오히려 생산성과 가독성을 해치는 오버 엔지니어링이 된다.

1) 과도한 추상화(Over-abstraction)의 문제점
- 파일 네비게이션 피로 (Context Switching):
  단순한 CRUD 기능 하나를 확인하거나 수정하기 위해 View -> Form -> Action -> Service -> Repository -> DTO/Interface 등 5~7개 파일을 널뛰기하듯 열어봐야 한다.
- 필드 추가 비용 폭증:
  테이블 컬럼 하나(예: `is_secret` 비밀글 여부)를 추가하는 단순 작업에도 연결된 모든 계층의 파일들을 동시에 열어 수정해야 하는 비효율이 발생한다.
- 껍데기 코드(Pass-Through)의 범람:
  비즈니스 로직이 전혀 없는데도 계층 구조를 맞추기 위해 상위 계층이 하위 계층 함수를 단순히 호출해서 리턴만 하는 무의미한 보일러플레이트 코드가 증가한다.

2) 추상화가 과해졌음을 알리는 3대 경고 신호 (Red Flags)
- 의미 없는 중계 함수: Service 계층의 코드가 `return await postRepo.findById(id);` 처럼 단순 전달 역할만 할 때.
- 1:1 대응 인터페이스: 교체 계획이나 다형성이 전혀 없는데도 관습적으로 단 하나의 구현체만을 위한 Interface/Repository를 남발할 때.
- 유지보수 속도 저하: 기능 구현 자체보다 계층 간 데이터 전달 규격(DTO, Type 매핑)을 맞추는 데 더 많은 시간이 소요될 때.

3) 실용주의적 아키텍처 판단 기준 (Pragmatic Approach)
- 작은 규모 / 초기 단계 (Colocation - 한곳에 모으기):
  Server Action 파일 하나 안에 입력 검증(Zod), 비즈니스 로직, DB 쿼리(Prisma 등)를 직관적으로 함께 작성한다. 코드의 시작과 끝이 한눈에 파악되어 개발 및 수정 속도가 가장 빠르다.
- 점진적 분리 시점 (Refactoring on Demand):
  미리 계층을 쪼개지 않고, 시스템에 '실제 중복과 복잡성'이라는 고통이 발생할 때 분리한다.
- 동일한 DB 쿼리가 3곳 이상의 다른 Action에서 중복 호출되기 시작할 때 -> Data Access Layer (`queries/`) 분리
- 권한, 검증, 외부 연동(알림, 결제 등) 조건문이 길어져 Action의 가독성이 떨어질 때 -> Application Layer (`services/`) 분리

**정리**
- "나중에 필요할지도 모른다"는 추측으로 미리 계층을 쪼개지 않는다 (YAGNI 원칙 - You Aren't Gonna Need It).
- 작은 프로젝트는 직관적인 수직 통합(Colocation)으로 시작하고, 규모와 복잡도가 임계점을 넘을 때만 점진적으로 계층을 분리하는 것이 가장 실용적이다.
