## 실험 1. Task CRUD를 Server Action 중심으로 구현

[실험방법]

'use server' 지시어를 선언한 비동기 함수(createTask, deleteTask)를 작성하고, <form action={createTask}>에 직접 바인딩한다.

작업 완료 후 revalidatePath('/tasks')를 호출하여 화면이 어떻게 갱신되는지 확인한다.

[실험결과]
별도의 fetch API 호출이나 클라이언트 상태(useState) 갱신 로직 없이도, DB 처리 완료 즉시 서버 컴포넌트가 최신 데이터로 다시 렌더링되어 UI가 자동으로 반영된다.

원인 및 동작 메커니즘: Server Action 호출 시 브라우저는 POST 요청으로 RPC(원격 프로시저 호출)를 수행하고, Next.js 서버는 액션 실행 후 revalidatePath를 통해 해당 경로의 RSC Payload를 새롭게 생성하여 클라이언트로 스트리밍한다. 클라이언트는 새로고침 없이 최신 DOM 트리만 교체하므로 코드가 극도로 단순해진다.

## 실험 2. 동일 Mutation 일부를 Route Handler로 구현하고 차이 비교

[실험방법]

동일한 Task 등록 기능을 app/api/tasks/route.ts의 POST 메서드(Route Handler)로 구현한다.

클라이언트 컴포넌트에서 fetch('/api/tasks', { method: 'POST', body: ... })를 호출하고, 수동으로 응답을 받아 상태를 업데이트한다.

[실험결과]
Route Handler 방식은 fetch 작성, JSON 직렬화/역직렬화, 에러 상태 처리, 수동 캐시 무효화(router.refresh()) 등 클라이언트 보일러플레이트 코드가 크게 증가한다.

원인 및 동작 메커니즘: Route Handler는 표준 REST API 엔드포인트이므로 외부 클라이언트(모바일 앱, 웹훅 등)와의 범용 통신에 적합하지만, Next.js 내부 폼 처리 및 UI 상태 동기화 관점에서는 Server Action이 React 생명주기 및 캐시 시스템과 밀접하게 결합되어 있어 생산성과 응집도 면에서 훨씬 유리하다.

## 실험 3. Client Validation 우회로 Server Validation 필요성 확인

[실험방법]

<input required minLength={2} />로 프론트엔드 검증을 적용한 후, 브라우저 개발자 도구(F12)에서 required 속성을 강제 삭제하거나 빈 공백 문자열로 전송을 시도한다.

서버 액션 내부에서 Zod 또는 유효성 검사 로직이 없을 때와 있을 때의 DB 상태를 비교한다.

[실험결과]
클라이언트 검증만 존재할 경우 속성 조작이나 콘솔 요청으로 손쉽게 우회되어 빈 값("")이 DB에 그대로 저장된다. 반면 서버 액션에 Zod 검증(taskSchema.safeParse)을 배치하면 클라이언트 조작과 무관하게 요청이 차단되고 안전한 에러 객체가 반환된다.

원인 및 동작 메커니즘: 클라이언트 사이드 검증은 오직 사용자 편의(UX)를 위한 가이드일 뿐 보안 경계선(Security Boundary)이 될 수 없다. 브라우저는 언제나 조작 가능한 신뢰할 수 없는 환경이므로, 데이터 정합성과 보안을 보장하는 최종 방어선은 반드시 서버 계층(Server Action/Backend)에 위치해야 한다.

## 실험 4. DB Access를 UI 파일에서 분리하는 리팩터링 (DAL 적용)

[실험방법]

Page/UI 컴포넌트 파일 내부에 직접 작성되어 있던 DB 쿼리(Prisma/Drizzle/SQL)를 완전히 걷어낸다.

src/lib/dal/task.ts (또는 src/data-access/task.ts) 파일을 별도로 생성하고 getTasks, createTaskInDb 함수로 쿼리를 격리한 뒤, UI와 Server Action에서는 이 DAL 함수만 호출하도록 리팩터링한다.

[실험결과]
UI 컴포넌트는 오직 '화면 표현'과 '사용자 인터랙션'에만 집중하게 되고, DB 스키마나 쿼리 방식이 변경되어도 UI 파일을 건드릴 필요 없이 DAL 파일 하나만 수정하면 전체에 일괄 적용된다.

원인 및 동작 메커니즘: 관심사 분리(SoC, Separation of Concerns) 원칙에 따라 Presentation 계층과 Data Access Layer(DAL)의 물리적 경계가 확립된다. 비즈니스 로직과 데이터베이스 결합도가 낮아져 스파게티 코드 형성이 원천 차단되며, 테스트 코드 작성 및 유지보수성이 비약적으로 향상된다.
