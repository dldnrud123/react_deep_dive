
# Pure Rendering / Event Handler / Effect의 역할을 구분한다.

- Pure Rendering : 순수하게 화면구성(jsx)을 위한 부분, sideEffect X
  실행시점 : 컴포넌트 함수 호출 시
  목적 : 화면출력

- Event Handler  : 사용자의 EventTrigger에 의한 동작을 정의하는 부분, 유저가 특정 동작 시
  실행시점 : 사용자가 특정 동작 시 (onClick, onChange 등)
  목적 : 유저 요청에 따른 트랜잭션 수행

- Effect : 외부의 시스템과 동기화를 정의하는 부분
  실행시점 : 컴포넌트가 화면에 다 그려진(Paint) 직후
  목적 : 리액트 상태와 외부 시스템(DOM/API)의 동기화

# Effect를 component lifecycle 대체제가 아닌 Synchronization 관점으로 설명한다.

전통적인 웹은 페이지 새로고침으로 DB 데이터를 새로 받아왔지만, SPA 환경에서는 컴포넌트가 화면에 유지된 채 내부 상태(검색 조건, 페이징)만 바뀐다. 
따라서, useEffect는 마운트 시점 한 번만 실행되는 생명주기 대체제가 아니라, 컴포넌트 내부의 '조회 조건(State)'이 바뀔 때마다 그에 맞는 '외부 DB 데이터'를 지속적으로 일치시키는 동기화 파이프라인으로 접근해야 한다.


# Effect dependency가 필요한 이유를 closure와 연결하여 설명한다.

아래 예시를 보자.

예시)
```jsx
function ChatRoom({ roomId }) {
  useEffect(() => {
    // 소켓에서 메시지가 올 때마다 실행되는 콜백 함수를 등록함
    chatServer.on('message', (msg) => {
      console.log(`[${roomId} 수신] ${msg.text}`);
    });

}
```

first 수신 : hi 라고 찍힐것이다 

(정리)
리액트의 모든 Hook과 함수는 특정 렌더링 시점의 '불변 스냅샷'을 바라본다.
의존성 배열(deps)은 컴포넌트의 데이터가 바뀌어 새로운 스냅샷이 생성되었을 때, 스냅샷을 최신화하도록 지시하는 스냅샷 동기화 장치다.

# Stale Closure를 재현하고 해결할 수 있다.

(문제코드)
```jsx
function StopWatch() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(() => {
      // 1회차 스냅샷(count = 0)만 영원히 바라봄
      setCount(count + 1);
    }, 1000);

    return () => clearInterval(timer);
  }, []); // 빈 배열: 마운트 시점 스냅샷에 갇힘

  return <h1>{count}초</h1>;
}
```

(수정코드1) 
```jsx
function StopWatch() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(() => {
      setCount(count + 1);
    }, 1000);

    return () => clearInterval(timer);
  }, [count]); // count가 바뀔 때마다 타이머를 갈아끼움 (비효율적)

  return <h1>{count}초</h1>;
}
```

(수정코드2)
```jsx
function StopWatch() {
  const [count, setCount] = useState(0);

// 마운트 시점에 타이머를 딱 "1번만" 켬
  useEffect(() => {
    const timer = setInterval(() => {
      // 리액트 내부 큐에 "기존 최신 값에 +1 해라"는 함수만 던짐
      setCount((prev) => prev + 1);
    }, 1000);

    // 컴포넌트가 화면에서 사라질 때 딱 "1번만" 타이머를 끔
    return () => clearInterval(timer);
  }, []); 

  return <h1>{count}초</h1>;
}
```

(수정코드3)
```jsx
function StopWatch() {
  const [count, setCount] = useState(0);
  const countRef = useRef(0); // 스냅샷에 묶이지 않는 고정 메모리 주소 확보

  useEffect(() => {
    const timer = setInterval(() => {
      // 1. 메모리 주소(current)의 값을 직접 1 증가
      countRef.current += 1;
      // 2. 최신 Ref 값을 읽어서 화면 리렌더링 트리거
      setCount(countRef.current);
    }, 1000);

    return () => clearInterval(timer);
  }, []); // 타이머는 1번만 켜지고 유지됨

  return <h1>{count}초</h1>;
}
```

# Cleanup이 필요한 외부 리소스를 판단할 수 있다.

백그라운드에서 실행되어 속도에 영향을 주는 경우

1. 네트워크 : fetch, axios (비동기 요청) 
  -> 이전 요청의 늦은 응답이 최신 화면을 덮어쓰는 경쟁 상태(Race Condition) 방지 및 불필요한 트래픽 차단 (AbortController로 취소)

2. 타이머 : setInterval, setTimeout
  -> 컴포넌트가 사라져도 백그라운드 큐에서 무한 실행되며 CPU를 점유하는 메모리 누수 방지 (clearInterval)

3. 전역 이벤트 : window.addEventListener
  -> 렌더링/마운트될 때마다 리스너가 중복 등록되어 동일 로직이 N번 실행되는 현상 방지 (removeEventListener)

4. 소켓/구독 : WebSocket, SSE, 외부 라이브러리 객체
  -> 끊어지지 않은 좀비 커넥션으로 인한 서버 자원(세션 풀) 고갈 방지 (socket.close(), chart.destroy())


# StrictMode에서 개발 중 Effect 재실행의 목적을 설명할 수 있다.

useEffect에서 cleanUp이 정상적으로 작동하여 남은 리소스로 인한 메모리누수 또는 버그같은 문제가 없는지 파악할 수 있는 검사기능. 

# State와 Ref의 차이를 render trigger 관점에서 설명한다.

State 변경 시 : render trigger O
  setState() 호출 -> 리액트 스케줄러 등록 -> 컴포넌트 함수 재실행(Virtual DOM diffing) -> 브라우저 화면 갱신

Ref 변경 시   : render trigger X
  ref.current = 값 -> 자바스크립트 힙(Heap) 메모리의 객체 필드만 바뀜 -> 끝 (리액트는 바뀐 줄도 모르고 관심도 없음)

# You Might Not Need an Effect 기준으로 불필요한 Effect를 제거할 수 있다.

1. 사용자 액션(클릭, 폼 제출, CRUD API 요청)
특정 이벤트 시점에 즉시 처리되어야 하는 단위 작업은 Effect가 아니라 eventHandler 내부에서 직접 처리한다.

2. Derived State
기존 State나 Props를 조합/가공/필터링해서 얻을 수 있는 값은 불필요한 State와 Effect를 만들지 않고, 컴포넌트 렌더링 본문에서 변수로 직접 계산한다. (불필요한 2회 렌더링 방지)

** Effect를 써야 하는 진짜 유일한 경우 **
유저의 직접적인 클릭 때문이 아니라, "화면에 나타났거나 특정 조건(URL, 쿼리 파라미터 등)이 변경되었을 때 외부 시스템(REST API, WebSocket, 브라우저 전역 이벤트)과 화면을 일치(동기화)시켜야 하는 경우"에만 제한적으로 사용한다.

예시 1 - Derived State

```jsx
const [items, setItems] = useState([]);
const [filteredItems, setFilteredItems] = useState([]); // 굳이 또 State 만듦

useEffect(() => {
  // items 바뀌었다고 Effect 켜서 또 set 침 -> 렌더링 2번 터짐
  setFilteredItems(items.filter(item => item.active));
}, [items]);
```
