## 주제 1 : Protected Route + Server-side authorization 구현 (Middleware)**

[실험방법]

비로그인 상태(쿠키 없음)로 브라우저에서 /admin 페이지 접속을 시도한다.

메인 페이지에서 임시 로그인 버튼을 눌러 쿠키를 굽고 다시 /admin 접속을 시도한다.

[실험결과]
비로그인 시 화면이 뜨지 않고 즉시 /login (또는 루트 경로)로 튕겨나가며, 로그인(쿠키 생성) 후에는 정상적으로 대시보드에 진입한다.
=> Next.js의 미들웨어가 요청을 가로채어 쿠키(session_token)의 존재 여부를 1차적으로 검사하기 때문이다. 토큰이 없으면 라우팅 자체를 차단하고 리다이렉트 시키는 Authentication(인증) 방어가 동작한 것이다.

## 주제 2 : 사용자별 접근 권한 실패 케이스 테스트 (Server Action)

[실험방법]

관리자 대시보드(/admin)에서 권한이 없는 임의의 유저('hacker')로 설정된 'DB 업데이트 시도' 폼 버튼을 클릭한다.

[실험결과]
미들웨어는 정상적으로 통과하여 화면에 들어왔음에도 불구하고, 업데이트가 실행되지 않고 Forbidden: 본인이 작성한 글만 수정할 수 있습니다 에러가 발생한다.
=> 미들웨어는 '로그인 여부'만 확인할 뿐 실제 게시글의 DB 소유권은 알지 못한다. 따라서 Server Action 내부에서 넘겨받은 유저 ID와 DB의 작성자 ID를 직접 비교하는 미시적 인가(Authorization) 처리를 거쳤기 때문에 2차 방어선에서 차단된 것이다.

## 주제 3 : cache / revalidation 조건을 다르게 설정해 freshness 비교

[실험방법]

랜덤 강아지 사진 API를 호출하는 /admin 페이지에서 F5(새로고침)를 여러 번 누른다.

이후 정상적인 권한(작성자 본인)으로 변경하여 DB 업데이트 액션을 성공시킨다.

[실험결과]
새로고침을 여러 번 해도 강아지 사진이 계속 똑같이 유지되다가, 업데이트 액션 성공 직후에만 새로운 강아지 사진으로 바뀐다.
=> Next.js의 fetch는 기본적으로 응답 결과를 캐싱(force-cache)하여 불필요한 중복 통신을 막기 때문이다. 하지만 데이터 업데이트 완료 후 revalidatePath('/admin')을 호출함으로써 해당 경로의 캐시 유통기한을 강제로 파기했고, 다음 렌더링 시 최신 데이터(Freshness)를 다시 가져오도록 유도했기 때문이다.

## 주제 4 : loading / error / empty / not-found 상태 구현

[실험방법]

데이터를 불러오는 과정에 3초의 통신 딜레이를 주어 화면 진입을 확인한다.

URL 쿼리스트링을 ?state=error 및 ?state=empty로 변경하여 강제 접속한다.

[실험결과]
딜레이 중에는 하얀 화면 대신 loading.tsx가 뜨고, 에러 발생 시 앱이 죽지 않고 error.tsx가 뜨며, 빈 데이터일 때는 not-found.tsx 커스텀 화면이 출력된다.
=> Next.js App Router는 파일 시스템 기반의 컴포넌트 렌더링을 사용하므로, 비동기(Promise)가 대기 중일 때는 가장 가까운 loading.tsx를 띄우고, 예외(throw Error)나 notFound() 함수가 실행되면 Error Boundary에 의해 미리 준비된 UI 컴포넌트로 렌더링을 안전하게 교체하여 앱 붕괴를 막기 때문이다.
