# 1. Authentication과 Authorization을 명확히 구분한다.

* **Authentication (인증):** "너 누구야?"를 묻는 과정. 사용자의 신원(아이디/비밀번호)을 확인하고 세션 토큰을 발급하는 로그인 절차 자체를 의미한다.
* **Authorization (인가):** "너 이거 할 권한 있어?"를 묻는 과정. 로그인한 유저가 관리자인지, 혹은 본인이 작성한 글인지(소유권) 확인하여 리소스 접근을 허용하거나 차단하는 절차를 의미한다.
* **결론:** 시스템 보안을 위해서는 '로그인 여부(인증)'만 확인할 것이 아니라, '해당 데이터의 조작 권한(인가)'까지 투트랙으로 분리하여 설계해야 한다.

---

# 2. Cookie / Session의 관계를 설명할 수 있다.

* 전통적인 웹 환경(PHP 등)과 동일하게 프론트엔드와 서버 간의 상태를 유지하는 핵심 메커니즘이다.
* **Session (세션):** 유저의 민감한 정보(유저 ID, 권한 등)를 서버 메모리나 DB 등 '서버 측'에 안전하게 저장하는 공간이다.
* **Cookie (쿠키):** 서버에 있는 내 세션 정보에 접근할 수 있는 열쇠(Session ID)를 브라우저(클라이언트) 측에 저장해 두는 수단이다. 브라우저는 요청을 보낼 때마다 이 쿠키를 서버로 전달하여 신원을 증명한다.

---

# 3. HttpOnly / Secure / SameSite의 목적을 이해한다.

발급된 쿠키(세션 키)를 해커로부터 방어하기 위한 필수 보안 옵션이다.
* **HttpOnly:** 자바스크립트(`document.cookie`)를 통한 쿠키 접근을 원천 차단하여, 악성 스크립트를 주입하는 **XSS 공격**을 방어한다.
* **Secure:** 오직 HTTPS 암호화 통신 환경에서만 쿠키가 전송되도록 강제하여, 네트워크 패킷 감청을 방어한다.
* **SameSite (Lax/Strict):** 다른 도메인(Cross-origin)에서 발생한 요청에는 쿠키를 실어 보내지 않도록 하여, 위조된 요청을 보내는 **CSRF 공격**을 방어한다.

# 4. 인증 확인과 권한 검사를 어느 계층에 둘지 판단한다.

Next.js 환경에서는 물리적/성능적 이유로 검사 계층을 분리하는 것이 최적의 아키텍처다.
* **인증 확인 (1차 방어선 - Middleware):** Vercel Edge Network 같은 라우팅 최전선에서 실행된다. 쿠키 유무만 빠르게 검사하여 비로그인 유저를 입구컷(리다이렉트) 시킨다.
* **권한 검사 (2차 방어선 - Server Action / Component):** 백엔드 서버(Node.js) 단에서 실행된다. 미시적인 데이터 소유권을 정밀하게 검증한다.

>  **[스터디 질의응답 & 인사이트]**
> **Q. 미들웨어에서 DB를 찔러 `SELECT level` 등 관리자 권한까지 한 번에 체크하면 안 될까?**
> A. 안 된다. 미들웨어는 DB 커넥션 모듈 자체가 동작하지 않는 초경량 엣지(Edge) 환경이다. 설령 API로 찌른다 해도, 모든 트래픽이 거쳐 가는 곳이라 심각한 성능 병목이 발생한다. 따라서 미들웨어는 단순 세션 체크(인증)만 하고 통과시키며, 상세 권한(인가) 감시는 비즈니스 로직(Action)으로 역할을 철저히 분리해야 안전하고 빠르다.

# 5. Proxy가 전체 authorization solution을 대체하지 않는 이유를 이해한다.

* Proxy(Middleware)는 가벼운 라우팅 통제 역할만 수행하기 때문에, 무거운 DB 커넥션 모듈(MySQL 등)을 돌릴 수 없는 환경적 제약이 있다.
* 설령 조회가 가능하더라도, 모든 트래픽이 지나가는 Proxy 단에서 매번 DB를 찔러 권한(Level, 소유권)을 확인하게 되면 캐싱의 이점이 사라지고 심각한 트래픽 병목 현상이 발생한다.
* 따라서 Proxy는 거시적 접근 제어(AuthN)만 담당하고, 세밀한 DB 검증(AuthZ)은 비즈니스 로직 내부로 위임해야 한다.

# 6. Static / Dynamic / Cached Data의 요구사항을 구분한다.

* **Static Data:** 빌드 타임에 완성되어 평생 변하지 않는 데이터 (예: 회사 소개 페이지).
* **Dynamic Data:** 주식 호가창, 통장 잔고처럼 매 요청마다 최신이어야 하는 데이터 (`fetch(..., { cache: 'no-store' })`). DB를 항상 새로 찌른다.
* **Cached Data (Data Cache):** 한 번 DB에서 조회한 결과를 서버 단에 캐싱해두고 재활용하는 JSON 데이터. 속도는 매우 빠르지만 데이터 썩음(Stale) 현상이 발생할 수 있다.

>  **[스터디 질의응답 & 인사이트]**
> **Q. 과거 PHP 시절에는 캐시 파기(Revalidation)를 안 해도 갱신이 잘 됐는데, Next.js는 왜 캐시가 문제인가?**
> A. PHP는 유저가 새로고침할 때마다 매번 맨땅에 헤딩하듯 DB에 쿼리를 찔러 화면을 조립했기 때문이다(항상 최신이지만 부하가 큼). 반면 Next.js는 한 번 가져온 데이터를 서버 측(백엔드 `.next/cache` 폴더)에 'JSON 형태의 냉장고'로 몰래 얼려두고 모든 접속자에게 이를 재활용해서 쏴준다. 따라서 DB를 수정하더라도 Next.js 서버의 캐시를 날려주지 않으면 화면에는 평생 옛날 데이터가 보이게 된다.

# 7. Revalidation과 freshness requirement를 연결한다.

* 데이터를 강력하게 캐싱(재활용)하는 Next.js 환경에서, 데이터 썩음 현상을 해결하고 최신성(Freshness)을 확보하기 위해 액션 직후에 `revalidatePath('/admin')`를 호출해야 한다.

>  **[스터디 질의응답 & 인사이트]**
> **Q. 다수의 유저가 동시에 글을 수정해서 `revalidatePath`가 연속 호출되면 꼬이거나 충돌(동시성 문제)이 나지 않을까?**
> A. 전혀 지장을 주지 않는다. 실제 데이터 충돌 방지 및 저장은 DB(MySQL)의 트랜잭션이 알아서 처리한다. `revalidatePath`는 남의 저장 프로세스를 방해하는 행위가 아니라, 단지 서버에게 "지금 네가 쥐고 있는 캐시 데이터 폐기(퇴거)해!"라고 쪽지를 남기는 행위일 뿐이다. 
> 
> **Q. 만약 이 설정을 안 해주면?**
> A. 화면이 영원히 갱신되지 않는다. 따라서 "기존 세입자(캐시)를 퇴거(revalidatePath)시켜야 다음 렌더링 때 DB에서 새 데이터를 찔러 최신 데이터를 갱신한다"는 흐름이 Next.js의 핵심 표준(Standard) 원리다.

# 8. loading / error / not-found 상태를 production UX의 일부로 설계한다.

비즈니스 로직에 `if-else`와 `try-catch`를 섞어 쓰던 과거 방식에서 벗어나, 파일 시스템 라우팅으로 앱 붕괴를 방어하는 모던 프로덕션 아키텍처다.

* **loading.tsx:** 통신 대기 중일 때 노출되는 스켈레톤 UI.
* **error.tsx:** 에러 발생 시 앱 붕괴를 막고 갈아끼워지는 Error Boundary.
* **not-found.tsx:** 빈 데이터 안내 껍데기 화면.

>  **[스터디 질의응답 & 인사이트]**
> **Q. `error.tsx` 파일 최상단에 굳이 `'use client'`를 적어야 하는 이유는 뭘까?**
> A. 에러 화면에 들어가는 "다시 시도하기(onClick)" 버튼 때문이다. 서버 컴포넌트에는 마우스 클릭 같은 DOM 이벤트 개념이 없으므로, 유저 상호작용(버튼)이 필요한 에러 복구 컴포넌트는 반드시 브라우저(클라이언트) 환경에서 동작하도록 선언해야 한다.
> 
> **Q. `not-found.tsx` 파일 안에는 아무 조건문도 없는데 어떻게 알고 화면에 뜨는 걸까?**
> A. 파일 자체는 '껍데기'일 뿐 지능이 없다. 핵심 비즈니스 로직인 `page.tsx`에서 DB 조회 후 데이터가 없을 때 `notFound()`라는 함수를 호출하면, 이것이 방아쇠(Trigger)가 되어 진행 중이던 렌더링을 멈추고 `not-found.tsx` 컴포넌트로 화면을 스위칭하는 원리다.
